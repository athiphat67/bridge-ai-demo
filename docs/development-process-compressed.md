# แนวทางการพัฒนาโครงการ Bridge AI

## 1. ภาพรวมโครงการ

Bridge AI เป็นระบบต้นแบบสำหรับสนับสนุนการประเมินการบาดเจ็บของแผ่นการเจริญเติบโตบริเวณข้อเข่าในผู้ป่วยเด็ก โดยใช้ภาพถ่ายรังสีร่วมกับข้อมูลทางคลินิกที่มีโครงสร้าง เพื่อแสดงผลการวิเคราะห์ในรูปแบบที่สามารถตีความและอธิบายได้

วัตถุประสงค์หลักของโครงการ คือการสนับสนุนการประเมินความเสี่ยงเบื้องต้นเกี่ยวกับผลกระทบของการบาดเจ็บต่อการเจริญเติบโตของกระดูก เช่น ความเสี่ยงต่อการหยุดโต การเอียงผิดรูปของกระดูก และความยาวขาที่อาจแตกต่างกันในอนาคต

โครงการนี้มีสถานะเป็น **prototype เชิงวิจัยและนวัตกรรม** มิใช่ระบบวินิจฉัยทางการแพทย์ และยังไม่ควรถูกตีความว่าเป็นผลิตภัณฑ์ทางคลินิกที่พร้อมใช้งานจริง

## 2. ปัญหาที่โครงการมุ่งแก้ไข

ในการดูแลผู้ป่วยเด็กที่ได้รับบาดเจ็บบริเวณ growth plate ของข้อเข่า ภาพถ่ายรังสีในระยะเริ่มต้นสามารถแสดงความเสียหายเชิงโครงสร้างได้ แต่ไม่สามารถสรุปผลลัพธ์ระยะยาวได้อย่างชัดเจนในทันที โดยเฉพาะประเด็นต่อไปนี้

- การหยุดการเจริญเติบโตของกระดูก
- การเกิดความผิดรูปเชิงมุม เช่น varus หรือ valgus deformity
- การเกิดความยาวขาที่ไม่เท่ากันในระยะต่อมา

ข้อจำกัดดังกล่าวทำให้การตัดสินใจทางคลินิกต้องพึ่งการติดตามอาการระยะยาวและดุลยพินิจของแพทย์เป็นสำคัญ Bridge AI จึงถูกวางบทบาทให้เป็นเครื่องมือช่วยประเมินความเสี่ยงล่วงหน้าและสื่อสารผลการวิเคราะห์อย่างเป็นระบบ

## 3. สถานะของระบบในปัจจุบัน

ภายใน repository ปัจจุบัน มีองค์ประกอบสำคัญ 2 ส่วน ดังนี้

### 3.1 Demo Application

ระบบส่วนนี้ประกอบด้วย

- `frontend/` พัฒนาด้วย React, Vite และ Tailwind CSS
- `backend/` พัฒนาด้วย FastAPI

แอปพลิเคชันดังกล่าวรองรับลำดับการใช้งานครบถ้วนในระดับการสาธิต ได้แก่

1. การเลือกเคสตัวอย่างหรืออัปโหลดภาพ X-ray
2. การกรอกข้อมูลทางคลินิก
3. การประมวลผล
4. การแสดงผล overlay, risk summary และ growth prediction

อย่างไรก็ตาม ผลลัพธ์ในระบบส่วนนี้ยังอาศัย metadata และตรรกะจำลองเป็นหลัก จึงยังไม่ใช่ผลจาก model inference ที่แท้จริง

### 3.2 Clinical Research Pipeline

ไฟล์ `Working Prototype/knee_prognosis_pipeline.py` เป็นกลไกการคำนวณเชิงตรรกะทางคลินิกที่แยกอยู่ต่างหาก โดยใช้สูตรและตัวแปรอ้างอิงทางการแพทย์เพื่อประเมิน prognosis

ส่วนนี้จึงมีบทบาทเป็นแกนหลักของการคำนวณเชิงคลินิกของโครงการ แต่ยังไม่ได้ถูกรวมเข้ากับ demo application ในลักษณะ end-to-end

### 3.3 ข้อสรุปของสถานะปัจจุบัน

เมื่อพิจารณาโดยรวม สถานะของระบบในปัจจุบันสามารถสรุปได้ว่า

- มีส่วนติดต่อผู้ใช้ที่ใช้งานได้จริงในเชิงการสาธิต
- มี pipeline เชิงคลินิกสำหรับการคำนวณ prognosis
- แต่ยังไม่เป็น AI prototype ที่เชื่อมต่อครบทั้งระบบ

## 4. เป้าหมายของการพัฒนาระยะถัดไป

เป้าหมายที่เหมาะสมของโครงการในระยะถัดไป มิใช่การพัฒนา medical AI system แบบครบวงจรในทันที แต่เป็นการยกระดับระบบปัจจุบันให้เป็น **prototype ที่ใช้งานได้จริงในเชิงโครงสร้าง**

prototype ดังกล่าวควรสามารถดำเนินการได้ครบใน 4 ขั้นตอนหลัก

1. รับภาพ X-ray และข้อมูลทางคลินิก
2. วิเคราะห์ภาพด้วย model จริงอย่างน้อยในระดับการระบุตำแหน่งที่เกี่ยวข้อง
3. ผสานผลจากภาพกับตรรกะทางคลินิก
4. แสดงผลผ่าน dashboard ที่ชัดเจนและสามารถตีความได้

หากระบบสามารถดำเนินการครบถ้วนตามลำดับดังกล่าว จะถือว่าโครงการได้ก้าวจากระบบสาธิต ไปสู่ prototype ที่มีแกนการทำงานจริง

## 5. ขอบเขตของ Prototype รุ่นแรก

Prototype รุ่นแรกควรประกอบด้วยองค์ประกอบสำคัญดังต่อไปนี้

- การรองรับการอัปโหลดภาพ X-ray และการเลือกเคสตัวอย่าง
- แบบฟอร์มสำหรับบันทึกข้อมูลทางคลินิก
- vision model สำหรับระบุตำแหน่งบริเวณที่เกี่ยวข้องกับ growth plate
- prognosis engine ที่อาศัยตรรกะทางคลินิกและสามารถอธิบายผลได้
- dashboard ที่แสดงภาพ ผลลัพธ์ และเหตุผลประกอบอย่างครบถ้วน

ในขณะเดียวกัน Prototype รุ่นแรกยังไม่จำเป็นต้องครอบคลุมประเด็นต่อไปนี้

- การเชื่อมต่อกับระบบ PACS หรือ workflow ระดับโรงพยาบาล
- ระบบสิทธิ์ผู้ใช้และ audit control ระดับองค์กร
- multimodal deep learning model แบบ end-to-end
- การกล่าวอ้างความแม่นยำเชิงคลินิกในระดับใช้งานจริง

การกำหนดขอบเขตในลักษณะนี้จะช่วยให้การพัฒนาเป็นไปอย่างเหมาะสมกับข้อมูลและทรัพยากรที่มีอยู่

## 6. รูปแบบสถาปัตยกรรมที่เหมาะสม

รูปแบบสถาปัตยกรรมที่เหมาะสมที่สุดสำหรับโครงการนี้ คือ **hybrid architecture** ซึ่งแบ่งการทำงานออกเป็น 2 ชั้นหลัก

### 6.1 Vision Layer

ชั้นนี้ทำหน้าที่วิเคราะห์ภาพ X-ray เพื่อระบุตำแหน่งของบริเวณที่เกี่ยวข้องกับ growth plate หรือบริเวณบาดเจ็บ และสร้างผลลัพธ์เชิงภาพ เช่น bounding box หรือ heatmap รวมถึง structured image features ที่จำเป็นต่อการประมวลผลในขั้นถัดไป

### 6.2 Prognosis Layer

ชั้นนี้ทำหน้าที่ผสานข้อมูลจากภาพกับข้อมูลทางคลินิก และคำนวณผลลัพธ์โดยใช้ตรรกะหรือสูตรอ้างอิงทางการแพทย์ เช่น ระดับความเสียหาย ทิศทางความเสี่ยง และการประมาณผลกระทบในช่วงเวลา 1, 3 และ 5 ปี

### 6.3 เหตุผลในการเลือก Hybrid Architecture

เนื่องจากชุดข้อมูลที่มีอยู่ในปัจจุบันยังมีขนาดจำกัด การใช้ machine learning ในขั้นต้นควรจำกัดอยู่ในส่วนที่ข้อมูลรองรับได้อย่างเหมาะสม คือการวิเคราะห์ภาพและการระบุตำแหน่งที่เกี่ยวข้อง ส่วนการพยากรณ์ผลระยะยาวควรยังคงอาศัย structured clinical logic ที่สามารถตรวจสอบและอธิบายได้

แนวทางดังกล่าวมีข้อดีสำคัญ 3 ประการ

- มีความเหมาะสมกับขนาดและคุณภาพของข้อมูล
- สามารถตรวจสอบและประเมินผลได้ง่ายกว่า
- ให้ผลลัพธ์ที่มีความสามารถในการอธิบายสูงกว่า

## 7. เทคโนโลยีที่เหมาะสม

เทคโนโลยีที่มีอยู่ใน repository ปัจจุบันถือว่าใกล้เคียงกับแนวทางที่เหมาะสมแล้ว โดยข้อเสนอแนะหลักมีดังนี้

### 7.1 Frontend

- React
- Vite
- Tailwind CSS

เครื่องมือชุดนี้เหมาะสมกับการพัฒนา dashboard แบบต้นแบบ และควรใช้ต่อเนื่องจากโครงสร้างเดิม

### 7.2 Backend

- FastAPI
- Python

ชุดเทคโนโลยีนี้มีความเหมาะสมต่อการจัดการ API, image preprocessing, model inference และการเชื่อม logic ทางคลินิกเข้าด้วยกัน

### 7.3 Data and Storage

- PostgreSQL สำหรับการจัดเก็บข้อมูลที่มีโครงสร้าง
- S3-compatible object storage สำหรับจัดเก็บภาพ X-ray และไฟล์ overlay

แนวทางนี้เหมาะสมกว่าการเก็บข้อมูลทั้งหมดไว้ใน container หรือในหน่วยความจำชั่วคราวของระบบ

### 7.4 AI/ML Tooling

- PyTorch
- YOLO-style object detector สำหรับ vision model รุ่นแรก
- NumPy, Pandas, Pillow และ OpenCV สำหรับ preprocessing และ data handling

เทคโนโลยีดังกล่าวเพียงพอสำหรับการพัฒนา prototype รุ่นแรก โดยยังไม่จำเป็นต้องเพิ่มเครื่องมือที่ซับซ้อนกว่านี้

## 8. ลำดับการทำงานของระบบ

ลำดับการทำงานที่เหมาะสมของ Prototype ควรมีโครงสร้างเป็น workflow เดียวที่เชื่อมโยงตั้งแต่การรับข้อมูลไปจนถึงการแสดงผล ดังนี้

1. ผู้ใช้อัปโหลดภาพ X-ray หรือเลือก sample case
2. ผู้ใช้กรอกข้อมูลทางคลินิกที่จำเป็น
3. Backend ตรวจสอบความครบถ้วนและความถูกต้องของข้อมูล
4. ระบบ preprocess ภาพให้อยู่ในรูปแบบที่พร้อมสำหรับ model inference
5. Vision model วิเคราะห์ภาพและระบุตำแหน่งที่เกี่ยวข้องกับ growth plate หรือบริเวณบาดเจ็บ
6. ระบบแปลงผลจากภาพให้อยู่ในรูป structured features
7. Prognosis engine ผสานผลจากภาพกับข้อมูลทางคลินิกและตรรกะทางการแพทย์
8. ระบบจัดเก็บผลลัพธ์ที่เกี่ยวข้อง
9. Frontend แสดงผลลัพธ์ในรูปแบบ dashboard ที่ประกอบด้วยภาพ overlay, ตัวชี้วัดสำคัญ, คำอธิบายความเสี่ยง และ growth projection

ในเชิงสถาปัตยกรรม ลำดับดังกล่าวสามารถสรุปเป็น pipeline flow ได้ดังนี้

```text
X-ray Image + Clinical Input
        │
        ▼
Input Validation
        │
        ▼
Image Preprocessing
        │
        ▼
Vision Model Inference
        │
        ▼
Image-derived Features
        │
        ├──────────────► Result Overlay
        │
        ▼
Clinical Logic / Prognosis Engine
        │
        ▼
Risk Summary + Growth Projection
        │
        ▼
Persistence Layer
        │
        ▼
Dashboard Output
```

เมื่อระบบสามารถดำเนินการครบตามลำดับดังกล่าวอย่างมีเสถียรภาพ จะถือว่า prototype มีโครงสร้างการใช้งานที่สมบูรณ์เพียงพอ

## 9. แนวทาง AI/ML และ Pipeline การวิเคราะห์

แนวทางที่เหมาะสมสำหรับโครงการนี้ คือการใช้ AI/ML เฉพาะในส่วนที่ข้อมูลรองรับได้อย่างเหมาะสม และให้การคำนวณเชิง prognosis อยู่บนพื้นฐานของ structured clinical logic ที่สามารถตรวจสอบได้

### 9.1 บทบาทของ Vision Model

Vision model ควรมีบทบาทหลักในการวิเคราะห์ภาพ X-ray เพื่อสกัดข้อมูลเชิงพื้นที่และข้อมูลเชิงลักษณะที่จำเป็นต่อการประเมินต่อไป โดยผลลัพธ์ขั้นต่ำที่ควรได้จาก model รุ่นแรก ได้แก่

- ตำแหน่งของ physis หรือบริเวณที่เกี่ยวข้องกับการบาดเจ็บ
- bounding box หรือ heatmap สำหรับการแสดงผล
- structured image features ที่ใช้ใน prognosis layer

ในระยะเริ่มต้น Model ไม่จำเป็นต้องรับผิดชอบการพยากรณ์ผลระยะยาวโดยตรง เนื่องจากข้อมูลที่มีอยู่ยังไม่เพียงพอสำหรับการฝึก end-to-end prognosis model อย่างน่าเชื่อถือ

### 9.2 โครงสร้างของ AI Pipeline

Pipeline การวิเคราะห์ภาพควรถูกออกแบบให้มีลำดับที่ชัดเจน ดังนี้

#### ขั้นที่ 1: Image Ingestion และ Preprocessing

ระบบรับภาพ X-ray ในรูปแบบที่กำหนด จากนั้นดำเนินการ preprocessing เช่น

- ตรวจสอบชนิดไฟล์และความสมบูรณ์ของภาพ
- resize หรือ normalize ภาพให้อยู่ในขนาดที่เหมาะสมกับ model
- เตรียมภาพสำหรับ inference โดยไม่ทำลายบริบทสำคัญของ anatomy

#### ขั้นที่ 2: Localization

Model รุ่นแรกควรทำหน้าที่ระบุตำแหน่งของ growth-plate region หรือบริเวณที่เกี่ยวข้องกับการบาดเจ็บเป็นหลัก โดยผลลัพธ์ของขั้นนี้มีความสำคัญต่อทั้งการแสดงผลเชิงภาพและการสร้าง feature สำหรับขั้นถัดไป

#### ขั้นที่ 3: Feature Extraction

หลังจากได้ตำแหน่งที่สนใจ ระบบควรแปลงผลดังกล่าวให้อยู่ในรูปของ structured image features เช่น

- ตำแหน่งของบริเวณบาดเจ็บ
- ขนาดหรือสัดส่วนของพื้นที่ที่เกี่ยวข้อง
- ลักษณะเบื้องต้นที่ใช้ในการประเมินความรุนแรง

ในกรณีที่มี model เสริมสำหรับ classification หรือ damage suggestion ผลลัพธ์จาก model ดังกล่าวควรถูกใช้เป็นข้อมูลสนับสนุน ไม่ใช่ผลตัดสินขั้นสุดท้าย

#### ขั้นที่ 4: Clinical Fusion

Structured image features จะถูกส่งต่อไปยัง prognosis layer เพื่อรวมกับ clinical inputs เช่น อายุ อายุของกระดูก เพศ น้ำหนัก ส่วนสูง ตำแหน่งบาดเจ็บ และปัจจัยทางคลินิกอื่น ๆ ที่เกี่ยวข้อง

#### ขั้นที่ 5: Prognosis Output

ระบบประมวลผลผลลัพธ์ให้อยู่ในรูปแบบที่พร้อมสำหรับ dashboard เช่น

- ระดับความเสียหาย
- ระดับความเสี่ยง
- แนวโน้มการเอียงหรือการหยุดโต
- การประมาณผลกระทบในช่วง 1, 3 และ 5 ปี

### 9.3 Pipeline Flow ในระดับระบบ

เพื่อให้เห็นภาพการเชื่อมโยงระหว่าง image analysis และ prognosis logic อย่างชัดเจน สามารถสรุป flow ได้ดังนี้

```text
Input Layer
├─ X-ray Image
└─ Clinical Form Data

Processing Layer
├─ Validation
├─ Image Preprocessing
├─ Vision Model
└─ Feature Structuring

Fusion Layer
├─ Clinical Variable Mapping
├─ Growth / Risk Logic
└─ Prognosis Computation

Output Layer
├─ Overlay Image
├─ Risk Metrics
├─ Growth Projection
└─ Explanation Factors
```

แนวทางดังกล่าวทำให้ระบบมีลักษณะเป็น **hybrid analytical pipeline** มากกว่าระบบ black-box และเหมาะสมกับสถานะของข้อมูลในปัจจุบัน

## 10. ระยะการพัฒนาที่เสนอ

การพัฒนาระบบควรดำเนินการเป็นลำดับสั้น กระชับ และมีเป้าหมายชัดเจน

### ระยะที่ 1: ปรับฐานของระบบให้พร้อมสำหรับของจริง

วัตถุประสงค์ คือการเปลี่ยน demo application ให้เป็น prototype shell ที่พร้อมเชื่อมต่อกับ model และ logic จริง

งานสำคัญประกอบด้วย

- คงโครงสร้าง frontend และ backend เดิมไว้
- ปรับ request/response contract ให้มีความชัดเจนและเสถียร
- เพิ่ม persistence สำหรับ cases, results และ images
- แยก demo-only logic ออกจาก real inference logic

ผลลัพธ์ที่คาดหวัง คือ product shell ที่พร้อมสำหรับการเชื่อม model และ pipeline จริง

### ระยะที่ 2: เพิ่ม Vision Model รุ่นแรก

วัตถุประสงค์ คือการแทนที่ visual output แบบ metadata-only ด้วย model inference จริง

งานสำคัญประกอบด้วย

- เตรียม training data จาก labeled X-rays ที่มีอยู่
- ฝึก localization model อย่างน้อย 1 ตัว
- เชื่อม model เข้ากับ backend
- ส่งคืน overlay ที่มาจาก inference จริง

ผลลัพธ์ที่คาดหวัง คือระบบสามารถสร้าง image-based localization ได้จริงโดยไม่ต้องพึ่ง metadata ที่เตรียมไว้ล่วงหน้าเป็นหลัก

### ระยะที่ 3: เชื่อม Prognosis Engine

วัตถุประสงค์ คือการแทนที่ simplified scoring ด้วย structured clinical logic ที่มีความเข้มแข็งกว่า

งานสำคัญประกอบด้วย

- เชื่อม image-derived features เข้ากับ clinical prognosis pipeline
- map ข้อมูลจากฟอร์มเข้าสู่ prognosis engine
- รวมผลลัพธ์ให้ออกมาเป็น analysis response ชุดเดียว

ผลลัพธ์ที่คาดหวัง คือระบบก้าวสู่การเป็น hybrid prototype อย่างแท้จริง

### ระยะที่ 4: ปรับปรุงประสบการณ์การใช้งาน

วัตถุประสงค์ คือทำให้ผลลัพธ์อ่านง่าย ใช้งานง่าย และเหมาะสมต่อการสาธิต

งานสำคัญประกอบด้วย

- ปรับข้อความและโครงสร้างการแสดงผล
- ทำให้ส่วนแสดงผลแต่ละส่วนมีความชัดเจน
- ดูแล sample cases ให้มีเสถียรภาพ
- เพิ่ม loading state, error handling และ edge-case behavior

ผลลัพธ์ที่คาดหวัง คือ prototype ที่สามารถใช้อธิบายและสาธิตได้อย่างมีประสิทธิภาพ

### ระยะที่ 5: Validation และ Deployment

วัตถุประสงค์ คือทำให้ระบบมีเสถียรภาพเพียงพอสำหรับการนำเสนอ การทดสอบ และการพัฒนาต่อ

งานสำคัญประกอบด้วย

- Deploy frontend และ backend แยกจากกัน
- Validate ผลลัพธ์ด้วย sample cases และ held-out cases
- จัดทำเอกสารอธิบายขอบเขตและข้อจำกัดของระบบ

ผลลัพธ์ที่คาดหวัง คือ hosted prototype ที่สามารถใช้งานได้จริงในเชิงสาธิตและมีคำอธิบายขอบเขตอย่างชัดเจน

## 11. ขอบเขตของบทบาท AI

การกำหนดขอบเขตของ AI เป็นประเด็นสำคัญเชิงสถาปัตยกรรมของโครงการ

### 11.1 สิ่งที่ AI ควรดำเนินการในระยะนี้

- ระบุตำแหน่งที่เกี่ยวข้องบนภาพ X-ray
- ช่วยจำแนก broad injury state ในกรณีที่ข้อมูลสนับสนุน
- สร้าง visual evidence และ structured image features สำหรับ prognosis layer

### 11.2 สิ่งที่ AI ยังไม่ควรถูกกำหนดให้ดำเนินการ

- ทำนายผลการเจริญเติบโตระยะยาวจาก raw X-ray โดยตรง
- จำแนก injury subtleties ทุกประเภทจาก dataset ขนาดเล็ก
- แทนการตีความของแพทย์

การกำหนดขอบเขตในลักษณะนี้จะช่วยให้ระบบมีความน่าเชื่อถือทางวิชาการและไม่กล่าวอ้างเกินกว่าข้อมูลรองรับ

### 11.3 หลักการของ AI Pipeline ที่เหมาะสม

AI pipeline ของโครงการนี้ควรยึดหลักการสำคัญดังต่อไปนี้

- ใช้ AI ในส่วนที่ข้อมูลสนับสนุนได้อย่างมีเหตุผล
- แยก image analysis ออกจาก prognosis computation อย่างชัดเจน
- รักษาความสามารถในการอธิบายผลลัพธ์
- เปิดทางให้มี human review หรือ clinical confirmation ในจุดที่ model ยังไม่ควรถูกใช้ตัดสินใจโดยลำพัง

หลักการดังกล่าวทำให้ระบบมีความสมดุลระหว่างความสามารถของโมเดล ความน่าเชื่อถือทางคลินิก และความเป็นไปได้ในการพัฒนา prototype ภายใต้ข้อจำกัดจริง

## 12. ความเสี่ยงหลักของโครงการ

### 12.1 ความเสี่ยงด้านข้อมูล

ชุดข้อมูลยังมีขนาดจำกัด โดยเฉพาะในส่วนของ fracture variation และข้อมูลผลลัพธ์ระยะยาว จึงมีความเสี่ยงต่อการตีความความสามารถของ model สูงเกินจริง

### 12.2 ความเสี่ยงด้านขอบเขตงาน

หากกำหนดขอบเขตของ prototype กว้างเกินไป ระบบอาจพัฒนาจนซับซ้อนเกินความจำเป็นและไม่แล้วเสร็จตามเป้าหมาย

### 12.3 ความเสี่ยงด้านโมเดล

การที่ localization model ทำงานได้ดี มิได้หมายความว่าผลการพยากรณ์เชิงคลินิกจะมีความถูกต้องสมบูรณ์ในทันที Prognosis layer จึงยังต้องถูกนำเสนอในฐานะ guided estimate

### 12.4 ความเสี่ยงด้านประสบการณ์ผู้ใช้

หากระบบแสดงผลลัพธ์ในรูปแบบตัวเลขโดยไม่มีเหตุผลประกอบ ผู้ใช้อาจตีความผลลัพธ์คลาดเคลื่อนได้ จึงจำเป็นต้องออกแบบ UI ให้แสดงข้อมูลเชิงอธิบายอย่างเพียงพอ

## 13. เกณฑ์ความเพียงพอของ Prototype

Prototype ควรถูกพิจารณาว่ามีความเพียงพอ เมื่อสามารถดำเนินการได้อย่างเสถียรในประเด็นต่อไปนี้

- รับเคสและข้อมูลทางคลินิกได้
- วิเคราะห์ภาพด้วย localization step ที่มาจาก model จริง
- ผสานผลจากภาพกับ structured clinical logic ได้
- แสดงผลที่อธิบายได้ภายใน dashboard เดียว
- ใช้สาธิตเชิงเทคนิคและเชิงผลิตภัณฑ์ได้อย่างมั่นคง

เกณฑ์ดังกล่าวเป็นตัวชี้วัดความสำเร็จที่เหมาะสมสำหรับระยะถัดไปของโครงการ

## สรุป

กระบวนการพัฒนา Bridge AI แบ่งเป็นสองช่วงชัดเจน:

**ช่วงที่ผ่านมา (7–22 มิ.ย.)**: ทีมสร้าง demo application ที่โชว์ workflow ครบตั้งแต่ input ถึง output ได้สำเร็จภายใน 15 วัน โดย Namthip เตรียมข้อมูลและพัฒนา clinical research pipeline คู่ขนาน Athiphat ขึ้นโครง backend/architecture และ Purich ออกแบบ UI/UX Demo นี้ขับเคลื่อนด้วย metadata ที่ label ไว้ล่วงหน้า ซึ่งเพียงพอสำหรับ proposal submission แต่ยังไม่ใช่ prototype จริง

**ช่วงถัดไป (สำหรับรอบ 2 และต่อไป)**: ระบบใช้สถาปัตยกรรม **Neuro-Symbolic AI** — แยก Neural Network (Branch A: YOLO detection → Binary classification → CycleGAN visualization) ออกจาก Symbolic Logic (Branch B: Clinical Math Engine จาก pipeline ของ Namthip) โดยมี human-in-the-loop เป็นตัวเชื่อม

แนวทางนี้ **ซื่อสัตย์กับข้อจำกัดของ data** (55 ภาพ, 18 fracture cases): ML ทำเฉพาะสิ่งที่ data รองรับ (localization, binary classification), สิ่งที่ต้องการ precision สูงกว่า (SH type, Area%) ให้แพทย์ยืนยัน, prognosis ขับเคลื่อนด้วยสูตรทางการแพทย์ที่มีฐานวรรณกรรม ทั้งระบบออกแบบให้ **upgrade ได้ทีละ module** เมื่อมี data มากขึ้นโดยไม่ต้อง rewrite — นี่คือ Scalability ที่แท้จริงของ Neuro-Symbolic design
